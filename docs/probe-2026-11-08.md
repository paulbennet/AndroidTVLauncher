## Features & media
- Every modern web feature tested is supported: CSS nesting, `:has()`, container queries, anchor positioning, scroll-driven animations, View Transitions, Popover, WebGL2, **WebGPU adapter**, WebCodecs, WASM SIMD.
- Missing: SharedArrayBuffer (no COOP/COEP), Media Session, speech synthesis (TTS was disabled on this TV).
- Codecs (MediaCapabilities): H.264, HEVC Main10/HDR10, VP9 Profile 0/2, AV1 (up to 4K60) all report supported, smooth and power-efficient. AC-3 / E-AC-3: no.
- HDR display media query: false. Widevine: `SW_SECURE_CRYPTO` only (L3). The web layer can't play HD DRM video; streaming stays in native apps.

## Conclusions
1. Memory is acceptable: about 2× Arc, but under davidr44's WebView launcher and the old Google TV home.
2. Rendering is the bottleneck (run 2 shows it is CPU-side raster, not GPU): blur, animated shadows, many simultaneous animations and full-screen shaders are 2–6× over budget.
3. Launcher-like scenes hold 60 fps throughput, but at 15–27 ms per frame. → Design rules in [design-rules.md](design-rules.md); re-measure with the deadline-based jank metric.

## What changed in our understanding
- **The ring fade passes and beats davidr44's figure even on his metric:** 4.2% of frames over 16.6 ms, against his 8.5%; p95 is 16.1 ms, down from 31.9.
- **Grid scrolling** went from 26.6 ms to 10.0 ms median, and the cause is **unknown**: the scroll scenario barely changed (its tiles only gained `position: relative` and an invisible `::after`), and both runs started the same way (install, then `probe.sh`). Background load on the TV may differ between runs. **Treat single runs as noisy; compare at least 3 runs before deciding anything.**
- **The bottleneck is not the app-side GPU.** `GPU_DURATION` stays at 3–5 ms even for 70–155 ms frames, so the cost is in Chromium's raster and compositing on the 32-bit ARM CPU. That GPU time covers only the app's RenderThread drawing the WebView output. The design rules still apply; the reason is CPU raster, not shader throughput.
- The deadline is often 33 ms (two vsyncs, because frames are pipelined), so a 25 ms frame is not jank. That is why "> 16.6 ms" overstated jank in run 1.

# Releasing the WebView while hidden (S13), 2026-11-08 22:56

Test: `scripts/release-test.sh`. It runs the heavy probe page, keeps another app (Settings) in front for 75 s, then returns to the launcher.
Raw data: [`probe-results/2026-11-08_225555-release/`](../probe-results/2026-11-08_225555-release/). Policy in `MainActivity`:
the WebView is destroyed 60 s after `onStop`, or at once on `TRIM_MEMORY_BACKGROUND`. It is rebuilt in `onStart`.
A renderer crash or kill now rebuilds the WebView (`onRenderProcessGone`) instead of crashing the app.

| PSS (MiB, ÷1000 KiB) | After heavy page | Hidden 75 s | Back on launcher |
|---|---|---|---|
| Launcher process | 73 | 86 | 75 |
| WebView renderer | 102 | **0, process gone** | 59 (new process) |
| **Total** | **175** | **86** | **134** |

- **`WebView.destroy()` alone does not free the renderer.** The first attempt (`2026-11-08_225017-release`) kept the same renderer pid with about 70 MB. Calling `WebViewRenderProcess.terminate()` (Android 10+) before `destroy()` frees it.
- **Rebuild cost:** 971 ms from new WebView to first frame with a fresh renderer, against 509 ms when the renderer survived. The user sees this as a short delay on the first Home press after more than a minute in another app.
- Open question: the launcher process itself (Chromium's browser side, about 70 MB) stays. Freeing it would mean ending the process, which brings back a full cold start (about 1.1–1.8 s).

# Return timing and process exit (S16, S17), 2026-11-08 23:08

Test: `scripts/return-test.sh 3`. YouTube is in front for 10 s, 75 s or 135 s, then the launcher is opened with `am start -W`
(the same launch path Button Mapper uses). The test used release = 60 s and exit = 120 s.
Raw data: [`probe-results/2026-11-08_230750-return/summary.tsv`](../probe-results/2026-11-08_230750-return/summary.tsv).

| Hidden | Launcher state on return | Activity shown (ms) | Page drawn (ms) | Hidden PSS: launcher + renderer (MB) | YouTube PSS (MB) |
|---|---|---|---|---|---|
| 10 s ×3 | HOT, WebView alive | 119 / 123 / 237 | already loaded | 121 / 148 / 149 | 164–177 |
| 75 s ×3 | WebView rebuilt | 169 / 175 / 212 | 769 / 774 / 1286 (from WebView start) | 70 / 80 / 80 + **0** | 161–183 |
| 135 s ×3 | COLD (process exited) | 920 / 944 / 978 | 1461 / 1493 / 1513 (from process start) | **0 + 0** | 180–190 |

**Decision:** release the WebView at **60 s** and end the process at **2 min** (`DEFAULT_EXIT_DELAY_MS = 120_000`).
- A cold return (about 1.5 s) is only 0.2–0.7 s slower than a WebView rebuild (0.8–1.3 s), but it frees 70–94 MB more for the app in front.
- Short hops of under a minute keep the 0.1–0.2 s hot return.
- Delays can be tuned without a rebuild: `am start -n com.weblauncher.tv/.MainActivity --el releaseDelayMs N --el exitDelayMs N`
  (`exitDelayMs 0` means never exit); `--ez resetTuning true` restores the defaults.
